Beyond Connector Identity: Verifiable Authority Across Multi-Agent Systems

A connector can execute an action. That does not establish who authorized it—or whether the authority survived delegation.

Edward D. ClarkEnterprise Architecture · Agentic AI6 November 2026

6 minute read

Multi-agent authorization

Simulated evaluation

All ideas

As AI systems evolve from individual assistants to networks of collaborating agents, one question becomes more difficult: Who authorized the action that a downstream agent is about to perform?

A connector may execute under a service identity, agent identity, or another technical principal. That explains which credentials were used. It does not, by itself, establish whether the originating user authorized the particular action. Identity, authority, and evidence are related—but distinct.

Where the trust boundary appears

Imagine a user asking a parent agent to examine an approved catalog. The parent delegates a read-only task to a child. The child may possess a connector technically capable of making purchases. The important question is not merely whether the child can call that connector, but whether the original grant permits that action.

Agent Transaction Assurance (ATA) explores a bounded delegation model: the originating principal, the parent grant, the child recipient, allowed actions and resources, monetary limits, validity period, and revocation status all contribute to an authorization decision. Each downstream delegation should preserve or narrow authority—never silently expand it.

A proposed authority boundary

The architectural distinction is deliberate: the policy decision should be evaluated before a downstream action, and the decision evidence should explain the authority chain, constraints, and result. The execution platform's own logs are useful operational records, but should not be the sole source of assurance.

From delegation evidence to execution enforcement

Engineering update · 7 November 2026. The ATA private reference implementation has progressed from illustrative allow/deny decisions to executable local tests of synthetic protected-resource behavior. Merged, CI-checked engineering increments cover delegated permit issuance, an HTTP resource that rejects unsigned or altered requests, single-use operation replay checks, and a separate SQLite-backed resource that revalidates revocation within the same transaction as a synthetic write.

These are deliberately distinct demonstrations. The HTTP resource and the atomic commit-time revocation reference are not yet integrated as one isolated enforcement service. The current tests do not establish authenticated agent workload identity, protected signing-key custody, direct filesystem bypass resistance, external-provider enforcement, or independently attested execution.

The central research question is becoming more concrete: can a delegated authorization decision be enforced at the protected action boundary, including when a downstream agent has access to broader credentials? The next work is to join authorization, workload identity, resource isolation, and commit-time revocation in one non-bypassable path.

What the evidence proves—and what it doesn't

The captured JSON contains synthetic principals, the parent-to-child chain, requested action and resource, decision, reason, and an illustrative HMAC signature. Tests of the private reference implementation exercise the expected policy outcomes and detect decision-trace tampering.

These samples are not independently authenticated execution evidence. The test key is illustrative; the public repository contains captured outputs rather than the executable implementation. The model has not been integrated into a live connector boundary, and it does not yet establish trustworthy issuer identity, production key custody, distributed revocation freshness, or third-party verification.

That distinction matters. A simulation can show how an authorization policy ought to behave. Production assurance requires enforcing that policy at the action boundary and establishing independently trustworthy evidence about what happened.

Evaluate the approach

The public ATA evaluation repository contains the scenario outputs, consolidated report, methodology, and explicit limitations. No installation is required to inspect the examples.

For a technical review, I would start with five questions: Who is authorized to issue delegations? Where is the check enforced before a tool executes? How is inherited scope narrowed? How fresh is revocation information? Who can independently verify the decision evidence?

As agents gain the ability to act, enterprise trust will depend not only on what they can do, but on what they can demonstrate they were authorized to do.
